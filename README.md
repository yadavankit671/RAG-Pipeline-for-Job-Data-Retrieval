# Job Postings RAG

A retrieval-augmented generation (RAG) application for searching and asking questions about job postings. The project cleans HTML job descriptions, summarizes them with Groq, stores searchable documents in ChromaDB, and uses Ollama to generate grounded answers through a FastAPI application.

## Features

- Cleans HTML-formatted job descriptions into structured plain text.
- Preserves job metadata such as title, company, category, location, and level.
- Summarizes each posting into company, responsibilities, requirements, benefits, and compensation fields.
- Stores one searchable record per job in a persistent ChromaDB collection using cosine distance.
- Supports semantic search with optional metadata filters.
- Returns answers with source job IDs and source metadata.
- Includes a small browser UI served by the FastAPI application.
- Resumes description processing by skipping jobs already fully summarized in ChromaDB.

## Architecture

```text
Data/raw/LF Jobs.xlsx
        |
        v
src/ingestion.py
        |
        +--> Data/cleaned/metadata.xlsx
        +--> Data/cleaned/description.xlsx
                         |
                         +--> src/metadata_chunking.py
                         |       +--> Data/json/metadata.jsonl
                         |       +--> ChromaDB metadata records
                         |
                         +--> src/description_cleaner.py
                                 +--> Data/json/description_clean.jsonl
                                         |
                                         v
                              src/description_chunker.py
                                Groq summaries + ChromaDB documents
                                         |
                                         v
                                  src/rag_engine.py
                                Chroma retrieval + Ollama answer
                                         |
                                         v
                                      src/app.py
                                  FastAPI API and web UI
```

The Chroma collection is named `job_postings`. Chroma computes embeddings for the stored document text using its configured embedding function. The query path retrieves the closest records, optionally applies metadata filters, and sends only the retrieved context to Ollama.

## Requirements

- Python 3.10 or newer is recommended because the code uses modern type syntax.
- A Groq API key for the description summarization step.
- Ollama installed and running locally for answering API queries.
- The Ollama model configured in `src/rag_engine.py` (currently `llama3.1`) pulled locally.
- The source workbook at `Data/raw/LF Jobs.xlsx`.

Install Python dependencies in a virtual environment:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
pip install -r requirements.txt
```

On Windows, PowerShell may require an execution-policy change for the activation command:

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy RemoteSigned
```

Install and prepare Ollama separately, then pull the configured model:

```powershell
ollama pull llama3.1
```

## Configuration and Security

The current scripts use absolute paths rooted at `D:\Assignment\RAG`. If the project is moved, update the path constants in `src/ingestion.py`, `src/metadata_chunking.py`, `src/description_cleaner.py`, `src/description_chunker.py`, and `src/rag_engine.py`.

Before running the summarization step, set the `GROQ_API_KEY` constant in `src/description_chunker.py` to your own key. Do not commit API keys to source control. The current implementation keeps the key in source and should be changed to read it from an environment variable before sharing the repository publicly; rotate any key that has previously been exposed.

The Groq model, Ollama model, Chroma path, collection name, concurrency, and optional processing limit are configured near the top of their respective source files.

## Build the Index

Run the complete preprocessing and indexing pipeline from the project root:

```powershell
python src/setup.py
```

The scripts run in this order:

1. `ingestion.py` reads the workbook and creates cleaned Excel files.
2. `metadata_chunking.py` writes `metadata.jsonl` and seeds metadata in ChromaDB.
3. `description_cleaner.py` converts HTML descriptions to cleaned JSONL.
4. `description_chunker.py` calls Groq for structured summaries and upserts the final searchable documents.

The description chunker can be run again safely: it checks the existing collection and retries only missing or incomplete records. Processing can take time because the script deliberately pauses between Groq requests to respect free-tier rate limits.

## Run the Application

Start the API from the project root:

```powershell
python src/app.py
```

Or run it with Uvicorn:

```powershell
uvicorn --app-dir src app:app --host 127.0.0.1 --port 8000
```

Open [http://127.0.0.1:8000](http://127.0.0.1:8000) for the browser interface. The API documentation is available at [http://127.0.0.1:8000/docs](http://127.0.0.1:8000/docs).

## API

### `POST /api/query`

Request body:

```json
{
  "question": "Find senior data analyst roles in healthcare",
  "top_k": 5,
  "job_level": "Senior Level",
  "job_location": "New York, NY",
  "job_category": "Data Science"
}
```

All fields except `question` are optional. `top_k` defaults to `5`. Filter values must match the metadata stored during ingestion.

Example PowerShell request:

```powershell
$body = @{
  question = "Which jobs mention Python and remote work?"
  top_k = 5
} | ConvertTo-Json

Invoke-RestMethod -Uri http://127.0.0.1:8000/api/query -Method Post -ContentType "application/json" -Body $body
```

Response shape:

```json
{
  "answer": "...grounded answer with citations such as [LF0001]...",
  "sources": [
    {
      "job_id": "LF0001",
      "job_title": "...",
      "company_name": "...",
      "job_location": "...",
      "job_level": "...",
      "distance": 0.123
    }
  ]
}
```

The answer is instructed to use only retrieved postings and to cite supporting job IDs. A low distance indicates a more similar Chroma result.

## Troubleshooting

- `Input file not found`: place the workbook at `Data/raw/LF Jobs.xlsx` or update the path in `src/ingestion.py`.
- `Missing dependency. Run: pip install groq`: install the requirements and verify that the active Python interpreter is the project virtual environment.
- Ollama connection or model errors: start Ollama and run `ollama pull llama3.1`.
- Empty or weak results: confirm that `Data/chroma_db` contains the `job_postings` collection and rerun `python src/setup.py` after changing the source data.
- Chroma filter errors: use exact metadata values for `job_level`, `job_location`, and `job_category`.

## Limitations and Future Improvements

- Paths should be converted to project-relative paths or environment-based configuration.
- The Groq key should be loaded from an environment variable or secret manager.
- The current pipeline creates one summarized document per job rather than multiple overlapping chunks.
- Retrieval is semantic only; hybrid keyword search and reranking could improve precision.
- There are currently no automated tests or health checks for the API, data pipeline, or external model services.
- A production deployment would need authentication, request validation limits, structured logging, and managed storage for secrets and the vector database.

## Dataset

The assignment dataset contains 1,000 job listings, 145 companies, and 7 job categories. The source fields include job ID, category, title, company, publication date, location, level, tags, and an HTML-formatted description. See `task.md` for the full field definitions and assignment context.
